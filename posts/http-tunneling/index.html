HTTP 隧道：把 TCP 封装成 HTTP 双向流

HTTP 隧道不是新概念，CONNECT 已经用了二十多年。这篇讲它的完整形态：地址信封怎么设计、TCP 怎么塞进请求体、以及为什么能跑在不给 socket 的 CDN 上。

0 先看一次普通的访问

在浏览器里输入 example.com，按下回车。这四步是所有后续讨论的起点：

  1. DNS：查 example.com 的 A / AAAA 记录，得到一个 IP。
  2. TCP：和那个 IP 的 443 端口做三次握手。
  3. TLS：发 ClientHello，里面有个 server_name 扩展（type 0x0000）写着 example.com；服务端回证书，双方协商出会话密钥。
  4. HTTP：加密通道里发出 GET / HTTP/1.1，带 Host: example.com。

注意"目标"这件事出现了三次，但含义不同：

  • DNS 把域名换成 IP；
  • TCP 连接只认 IP + 端口，不认域名；
  • SNI 和 Host 又 redundantly 带上域名，是为了让同一台服务器上的多个站点能被区分。

记住这个事实：连接本身只认 IP + 端口，域名的信息要靠额外字段携带。后面所有代理协议的设计，都是围绕"怎么把目标地址塞给中转方"展开的。

1 绕一条路：代理要回答的两个问题

代理就是让流量多绕一跳：客户端连代理，代理再连目标。于是立刻出现两个问题。

问题一：代理怎么知道我要连哪里？ 客户端连的是代理的 IP，目标地址不在 TCP 头里。必须由应用层显式告诉它。

问题二：代理怎么知道我在说什么？ 如果只传目标地址，代理还得理解后面的内容才能转发；如果它不理解，就只能当一根管子。

历史上三种解法，正好对应三种思路。

1.1 HTTP 代理：把完整 URL 塞进请求行

最古老的做法。客户端不请求 /，而是请求完整地址：

text
GET http://example.com/index.html HTTP/1.1
Host: example.com

代理看到绝对 URI，自己再去连 example.com。缺点是只适用于 HTTP——它是"代理理解协议"的思路，代理必须解析 HTTP 才能转发。

1.2 HTTPS 代理：CONNECT，之后只搬字节

HTTPS 没法这么做，因为 URL 在 TLS 里面，代理看不见。于是有了 CONNECT：

text
CONNECT example.com:443 HTTP/1.1

代理回 200 Connection Established，之后这条 TCP 连接就变成了纯粹的字节管道——客户端在里面跑自己的 TLS，代理完全不知道内容是什么。

这一步是整篇文章的转折点。 "CONNECT 之后只搬字节"确立了一个模型：隧道协议只需要解决"目标地址怎么表达"，不需要理解载荷。VLESS、Trojan、Shadowsocks，以及后面所有的边缘隧道，都是这个模型的变体。

1.3 SOCKS5：把地址做成一个结构体

SOCKS5 把这个模型标准化了。握手协商完认证方式后，客户端发一个请求：

text
VER(1B) | CMD(1B) | RSV(1B) | ATYP(1B) | DST.ADDR | DST.PORT(2B)

CMD:  0x01 CONNECT  0x02 BIND  0x03 UDP ASSOCIATE
ATYP: 0x01 IPv4(4B) 0x03 域名(1B 长度 + n 字节) 0x04 IPv6(16B)

这段结构值得记住，因为它就是"地址信封"的原型：一个类型字节说明地址是什么形态，然后是地址本体，最后两字节端口。VLESS 和 Trojan 的请求段几乎是照抄。

到这一步，代理的原理已经完整了：信封（目标地址）+ 管道（原始字节）。剩下的一切复杂度都来自两个额外的需求：加密，和让流量看起来不像代理。

2 信封要藏起来

明文 SOCKS5 有两个致命问题：任何中间设备看到 0x05 开头加一段固定结构就知道这是代理；内容也是明文，可以被审查。

解法分两派。

2.1 VLESS：自己不加密，全靠外层

VLESS 的做法是把"加密"这件事完全外包给 TLS，协议本身只负责送地址：

text
1B version | 16B id | 1B optLen | opts | 1B cmd | 2B port | 1B atyp | addr | payload
  • cmd：1 = TCP，2 = UDP。
  • atyp 与 SOCKS5 同构：1 = IPv4，2 = 域名，3 = IPv6。
  • IPv4 目标下，头部最小 26 字节（1+16+1+0+1+2+1+4）。
  • 服务端收到后只回 2 字节 [version, 0]，表示"已受理"。

两个容易讲错的地方：

第一，那 16 字节不是密钥。 它是路由/身份标识，作用相当于"这个请求属于哪个用户"。VLESS 不做任何加密，它的安全性 100% 来自外层 TLS。把它当成加密协议，就会得出"VLESS 可以裸奔"的错误结论。

第二，它没有失败响应。 认证失败、目标不可达，服务端都是直接断开。用"连接是否继续"表达错误，代价是：在明文环境下，探测者可以靠"连上后是否保持"来区分服务。这也是它必须套 TLS 的原因之一。

2.2 Trojan：密码哈希摆在最前面

text
SHA-224(password) 的 hex(56B) | CRLF | 1B cmd | 1B atyp | addr | 2B port | CRLF | payload

SHA-224 输出 28 字节，转成十六进制正好 56 字节，所以判据是硬编码的：长度 ≥ 58 且第 56、57 字节是 0x0d 0x0a，命中就逐字节比对那 56 字节哈希。这个"密码写在明处"的设计不是失误——Trojan 的整个思路就是"让它看起来像一段正常的 HTTPS 流量"，而 HTTPS 的第一段本来就是随机字节，多一段十六进制串并不显眼。

它的代价同样明确：主动探测可以直接拿一个密码去试，服务端是否响应会泄露信息。所以 Trojan 必须跑在真的 TLS上，靠外观而不是靠密码学来保护自己。

2.3 Shadowsocks：协议层自己做加密

前两者把安全交给外层，Shadowsocks 反过来，自己就是加密协议：

text
masterKey = EVP_BytesToKey(password)              // 反复 MD5 拼接到 keyLen
salt      = random(keyLen)                        // 每条连接一个
subkey    = HKDF-SHA1(salt, masterKey, "ss-subkey")
chunk     = 2B 长度密文 + 16B tag | 数据密文 + 16B tag

几个必须准确的点：

  • EVP_BytesToKey 的迭代次数是 1——本质上是"反复算 MD5 直到够长"。它没有内存硬化，安全性完全取决于口令强度，不是现代 KDF。
  • nonce 12 字节、每帧递增。AEAD 的硬约束是 nonce 绝不重复，重复一次就等于把密钥流复用，直接可破。
  • 长度域也必须加密。否则长度本身就是可分析的特征：一个请求头多大、一个响应多大，都写在明文里。
  • 单帧载荷上限 0x3FFF，超了必须切分。
  • 2022 版规范补的正是早期设计的两个洞：salt 重放防护（防重放攻击）和固定长度头（防长度指纹）。

这三个协议放在一起看，能看出一条清晰的分歧线：安全交给外层（VLESS）／靠外观伪装（Trojan）／自己做加密（Shadowsocks）。三种选择的代价各不相同，没有一种在所有场景下都占优。

2.4 三种协议怎么在一台机器上共存

不需要端口区分，看第一块数据长什么样就行：

  • 长度 ≥ 58 且 data[56]==0x0d && data[57]==0x0a → 试 Trojan，比对哈希。
  • 否则按 VLESS 解。
  • 第一块是随机 salt，无法从结构判断 → 只能靠 URL 参数显式声明是 Shadowsocks。

最后一条是这个方法的边界：能结构判定的就结构判定，不能的必须带外声明。任何"自动识别协议"的方案都绕不开这一点。

3 换个玩法：不自己买服务器

上面所有方案都需要一台自己的服务器。有没有可能不买？

CDN 的边缘节点看起来是个诱人的替代品：全球分布、离用户近、有免费额度、出口 IP 是 CDN 自己的（在很多网络环境里是白名单）。

问题只有一个，但很致命：边缘节点不给你 socket。

你能上传的是一段代码，平台在每次 HTTP 请求到达时调用它：

js
export default {
  fetch(request, env, ctx) { ... }
}

就这样。没有 listen，没有 accept，没有常驻进程，函数返回后内存状态全部消失。

于是问题变成了：能不能只用 HTTP 请求和响应，表达一条 TCP 连接？

3.1 三条约束

答案取决于三个事实，它们决定了后面所有设计：

其一，入口是 fetch，而且名字必须叫 fetch。 这是模块式 Worker 的入口约定（Service Worker 时代对应 addEventListener('fetch')），导出的键名不对，平台就不会调用你。同时 fetch 也是唯一能拿到 request.body（一个 ReadableStream）并返回 response.body 的位置——唯一能做双向流式传输的地方。

其二，出站 TCP 是有的，但不可靠。 平台提供建立 TCP 连接的能力（Workers 里是 request.fetcher.connect），但受端口策略与网络路径影响，到部分目标的建连会直接失败或极慢。这条约束直接推出了后面第 5 节的"中转节点"。

其三，没有 UDP。 没有 UDP socket，任何"完整支持 UDP"的承诺在这个运行时上都不成立。

还有一条隐性约束：单次请求有 CPU 时间和内存上限（Workers 是 128MB 量级），这决定了所有队列都必须有界。

3.2 唯一的技巧：让 fetch 不返回

既然入口是一次调用、返回即结束，那就别返回。

请求体当上行管道，响应体当下行管道，函数挂在那里，把字节搬完为止。一条 HTTP 请求的生命周期被拉长成一条连接的生命周期。

这就是全部秘密。剩下的工作，是把"TCP 连接"翻译成 HTTP 能表达的形式。

4 载体层：三条把字节塞进 HTTP 的路

要让请求体/响应体承载字节流，有三种可用的 HTTP 形态。它们不是三选一的技术选型，而是三种伪装程度不同的方案。

4.1 WebSocket

客户端发 Upgrade: websocket 的 GET，服务端回 101。之后协议不再是 HTTP。

帧头最小 2 字节：1B FIN/RSV/opcode + 1B MASK/len，长度 126 时后接 2B、127 时后接 8B。客户端到服务端方向的 payload 必须掩码，所以每帧固定多 4 字节掩码键，服务端还要逐字节 XOR 还原。

好处是实现简单、全平台支持；坏处是 Upgrade 这个特征太明显，做流量分析的设备一眼就能挑出来。

有个优化叫 early data：客户端把首包 base64url 编码后塞进 Sec-WebSocket-Protocol，服务端在回 101 之前就能解出目标地址并开始建连，省一个 RTT。它的容量受 HTTP 头大小限制，够放一个 ClientHello。注意它只是"提前送数据"，与 TLS 的 0-RTT 会话恢复毫无关系——两者常被混为一谈。

另外，平台对空闲 WS 连接有超时，长连接需要应用层心跳；而 VLESS 协议本身不带心跳，心跳只能由客户端发。

4.2 gRPC

POST + content-type: application/grpc，本身就是 HTTP/2 上的双向流。每条消息前缀 5 字节：

text
1B 压缩标志 | 4B 大端长度 | protobuf 载荷

载荷是"一个 bytes 字段"的最小编码 0x0a <varint 长度> <数据>。0x0a 是 field 1 + wire type 2，所以"包一层 protobuf"实际只花 1~5 字节，不需要 schema，不需要 codegen。实现里只做切帧和拼帧。

这里有个坑：HTTP/2 有流控，初始窗口 65535 字节，窗口不更新写入就会阻塞。所以下行不能攒完再发，必须边读边写，把窗口管理交给运行时。

4.3 长 POST（stream-one）

最干净的一种：请求体即上行，响应体即下行，首包不编码，直接就是协议头。

三者里单位开销最低：无帧头、无掩码、无 protobuf 包装。

它的变体是 split 模式——上行、下行各一条请求，靠 path 里的会话 ID 关联。但在纯边缘函数里，这要求跨请求共享状态，只能落到 KV 或 Durable Object，多一次 RTT 加一次存储读写。所以不引入外部状态的唯一选择就是 stream-one。

4.4 对照

WebSocket gRPC stream-one
每消息额外开销 2~14B 头 + 4B 掩码 5B + 1~5B protobuf 0
首包能否提前 能（子协议头） 能（第一帧） 能（body 首位）
服务端识别特征 Upgrade content-type 无
上行写入 同步入队 需 await 需 await

三种载体解出来的都是同一份字节，交给同一个协议层。传输与协议正交，是这套实现里最干净的设计。

5 出站：为什么直连不够

拿到目标地址之后，接下来要真的连过去。前面说过，这个运行时的出站 TCP 不完备。于是实际实现把"直连"降级成"首选"，并把兜底做成必需。

5.1 并发竞速

同时发起 N 路 connect()，Promise.any 取最先 fulfilled 的。

关键细节：Promise.any 不会取消落败的 Promise。落败的 socket 必须显式 close，否则每个请求都在泄漏连接。超时同理，需要定时器或 AbortController 主动关。

并发两路压的是尾延迟，不是均值：单路失败的绝对值再小，乘上请求量也显著。

5.2 中转：把首包原样丢过去

连不上时，连到部署在平台网络内的中转服务，把客户端首包（TLS ClientHello 或 HTTP 请求）原样写入，由中转侧自己判断目标：

  • TLS：从 ClientHello 的 server_name 扩展（type 0x0000）取 SNI；
  • HTTP：取 Host 头。

这个设计的好处很明显：中转方完全不需要懂 VLESS 或 Trojan。它只看 SNI/Host，就能知道往哪转。一套中转服务可以服务所有客户端实现，与协议解耦。

代价同样明显：多一跳，且中转不可用时整条链路不可用。

5.3 地址池与确定性洗牌

中转地址不能写死。做法是 DoH 查询，顺序 TXT → A → AAAA。TXT 优先是因为一条记录能返回多个 ip:port，省掉 N-1 次往返。

拿到候选后，用 hash(目标域名 + 用户标识 + ip) 排序取前 N。这是简化的一致性哈希：同一组 (目标, 用户) 永远命中同一批出口。

为什么必须确定性？随机选会导致同一目标每次走不同出口 IP：触发风控、打断连接复用、还让故障无法复现。

5.4 决策顺序

图中「转发 → 重拨」那条边值得单独说：判据是 首字节到达，不是"握手成功"。中间设备可以先完成三次握手再静默丢弃——只判断 connect() 成功，会把这种情况当成正常连接，然后在下行方向一直空转到超时。

5.5 顺带：为什么有人在这里手写 TLS

平台给的是裸 TCP，没有 TLS。要连 HTTPS 代理、或做代理可用性探测，就得自己跑完整个握手：X25519 密钥交换（当时 WebCrypto 不支持，只能纯 JS 实现）、HKDF 的 extract/expand、AES-GCM 与 ChaCha20-Poly1305。

这件事最大的意义是打破一个直觉：TLS 不是黑盒，它只是一段可以在 JS 里跑完的字节协议。

6 搬运层：把字节从一头搬到另一头

协议解完了，连接也建好了，剩下的看起来就是 pipe。实际有三个坑。

6.1 合包

上行攒到 20KB 再 write；下行聚合上限 32KB，尾阈 512B，低水位 4KB，最多 4 轮、每轮 1ms 观察后强制 flush。

这等价于用户态 Nagle。省两类开销：write 的固定成本，以及 WS 帧头 + 掩码随包数线性增长的代价。1ms 的观察窗口是有原因的——TCP delayed ACK 在 40ms 量级，攒太久反而被 ACK 延迟放大。

6.2 有界队列

上行队列上限 16MiB / 4096 条，超限直接断连。

原因是内存上限：单个请求占用过多，并发几个就整体 OOM，而被终止的是整个 isolate，不只是这条连接。宁可断一条，不能拖垮全部。

6.3 世代号

连接会重拨，但旧连接上的读循环、定时器、EOF 回调不会立刻消失，可能在几百毫秒后才返回，然后把新连接的状态写坏。

js
if (wrapper.generation !== myGeneration || wrapper.socket !== mySocket) return;

isClosed 这类布尔标志不够用：它能表达"关没关"，不能表达"关过又开了"。凡是"取消 + 重建"并存的异步系统，单调递增的世代号是唯一可靠的判据。

6.4 两种等待策略

WS 上行同步入队、不 await：阻塞读循环会让 TCP 接收窗口停止更新，对端被限速。 HTTP body 流必须 await writer.ready：不等待等于放弃背压，内存按入站速率增长。

同一个数据面两种策略，取决于底层写入是否自带流控。

7 UDP 为什么最后只剩 DNS

没有 UDP socket。所以 UDP 命令只放行 53 端口：把 DNS 报文转成 DNS over TCP（2 字节长度前缀 + 报文）发给公共解析器，再把响应包回客户端。

为什么不做 UDP ASSOCIATE 模拟？因为它既打不了 NAT 洞，也保不住映射状态。

结果是确定的：QUIC（HTTP/3）、游戏、VoIP 全部不可用，只有域名解析能用。这是约束下的产物，不是设计取舍。

8 外围：订阅与伪装

前面讲的是数据面。要让真实客户端用起来，还需要两件外围工作。

订阅分三段：看 UA 或参数决定输出格式（Clash YAML / sing-box JSON / base64 链接列表）→ 拼分享链接 → 占位符替换（先用全零 UUID 和示例域名出模板，再替换真实值）。

里面的"优选 IP"原理是任播：同一个 IP 在不同地理位置落到不同机房，选就近入口等于直接降 RTT 和丢包。所以订阅里塞一批 IP 让客户端自己测速，比服务端替它选更准。

伪装三条可验证的做法：

  1. 未匹配路径反代真实站点，响应文本里替换 Host，让扫描器拿到合理内容。
  2. robots.txt 全禁；管理接口只对已认证请求返回内容；未配置时返回 404 而不是异常栈——异常页会直接暴露运行时和技术栈。
  3. 域名、关键字拆段在运行时拼接。这只对抗静态扫描，对主动探测无效。

真正的防线始终是 TLS + 真实站点外观，不是字符串拆分。 伪装只能提高成本，不能提供安全保证。

9 回到开头那条连接

现在对照第 0 节的四步，看同一个浏览器请求走完这条链后变成了什么：

步骤 直连时 走隧道时
DNS 解析目标域名得到目标 IP 解析你的域名，得到 CDN 的任播 IP
TCP 连到目标 IP:443 连到最近的边缘节点:443
TLS SNI = 目标域名 SNI = 你的域名，终点是边缘节点
HTTP 一个 GET / 一条长连接（WS / gRPC / 长 POST）

前四步全部照旧，只是终点从源站换成了边缘节点。真正的新东西发生在边缘节点内部：

  1. 从载体层剥出字节；
  2. 按协议头解出目标地址和载荷；
  3. 从边缘节点发起第二次 TCP 连接——这一次的目标由信封决定；
  4. 双向合包搬运，直到任一方 EOF。

所以"一个 HTTP 请求变成一条 TCP 连接"这句话的字面含义是：外层那条 HTTP 连接没有关，它承担了内层 TCP 连接的出入。一条请求的生命周期，被借来当作一条连接的生命周期。

10 边界

  • 多数 CDN 平台的服务条款禁止此类转发，滥用导致账号封禁，与实现质量无关。
  • 依赖中转生态：中转不可用，直连成功率不足以保证可用性。
  • 单实例只承载一套身份配置（配置是模块级全局变量，无法多租户）。
  • 无 UDP、无 QUIC，交互式实时应用不可用。
  • 涉及网络访问的合规问题，不同司法辖区要求不同，部署前先确认平台条款与当地法律。
